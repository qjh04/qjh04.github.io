go-wonderland项目

核心业务场景是什么？（如：产品定位、核心功能）

这是一个为智能语音/儿童陪伴类 IoT 设备提供的后端服务，整合 ASR/TTS/LLM、音色克隆和多角色对话能力，负责设备接入、对话编排、用户与设备管理及运营相关功能。

用到的关键技术点有哪些？核心开发功能中哪些具有技术挑战性？

  • 实时语音流水线编排难

    • 将 WebSocket 音频流、ASR 识别、TTS 播报、LLM 对话串成一条低延迟的异步流水线，同时要处理分段音频、goroutine 并发与异常恢复，保证对话实时性和稳定性。

  • 多用户 / 多设备 / 多角色的状态与权限难

    • 同一个用户下多设备、多角色参与群聊，请求可能针对多角色，既要保证对话上下文在缓存与数据库中一致，又要保证 HTTP 用户身份与 WebSocket 设备连接正确绑定、权限不越界。

  • 音色克隆与自定义音色闭环难

    • 涉及音频上传、临时文件安全处理、调用外部 clone 服务、OSS 存储，以及围绕用户/平台/语言/标签等维度的查询与权限控制，设计与实现都偏复杂。

流式对话结果的处理流程是什么？如何实现文本拼接、分割与 TTS 音频生成的联动？

流式对话结果处理 = LLM 的增量文本先通过 StreamingSegmenter 做“累积 + 按标点智能切句”，每切出一整句就立刻调用 DispatchTTSRequest 做流式合成，TTS 的音频分片再通过 WebSocket 持续下发到设备，从而实现“边生成边说、句子级触发”的联动效果。以一次 LLM 流式回复为例，简化时序如下：

  1. LLM 通过流式接口返回文字块：”今天” → “今天天气” → “今天天气很好。”…

  2. 每个块进入 StreamingSegmenter.SplitTextStream(chunk, false, sendToTTS)：

​ 暂时没有句号时，只累计不发；

​ 收到 “很好。” 时，识别到 。，切出 “今天天气很好。”，回调 sendToTTS(…)。

  1. sendToTTS 内部调用 DispatchTTSRequest(“今天天气很好。”, voiceType, onAudioChunk)：

​ 后端 TTS 产生多段音频分片，通过 onAudioChunk 逐段推送到设备。

  1. LLM 最后一个块到达，is_last=true：

​ 把剩下未凑成完整句子的部分（如果有）也一次性发给 TTS，做“收尾一句”的合成。

  1. 设备播放完毕上报 EventPlayEnd，服务器根据当前对话/群聊状态决定是否继续下一句/下一角色。

衡量该产品用户体验的关键技术指标有哪些？

  • 端到端响应时延

    • ASR 整段时延：从用户说完（AudioStatusEnd）到拿到完整识别文本的时间（ExecutionEventASR）。

    • 首字/首音时延：从用户说完到设备开始说话（第一段 TTS 音频播放）耗时。

    • 整轮对话时延：从用户说完到设备说完一整句或一整轮群聊的总耗时。

  • 识别与理解质量

    • ASR 识别准确率/错误率：可用“有效 ASR 文本占比、纠错比例、重复说比例”等近似衡量（代码里有 AsrWordCount 累加，可以扩展为“无效/重试次数”）。

    • LLM 回复满意度代理指标：如平均对话轮数、用户中断率（说到一半就打断）、常见拒答/无效回复占比。

  • TTS 播放体验

    • TTS 合成成功率：TTS 请求错误率、超时率。

    • TTS 连续播放平滑度：音频分片丢失率、播放中断次数、打断重播次数（AudioStatusAbnormal / EventPlayEnd 相关）。

    • 音色一致性：对于 clone 音色，失败率、降级到默认音色的比例。

  • 对话连续性与稳定性

    • 长连接稳定性：WebSocket 断线率、平均在线时长、重连次数（[CONNECT]/[DISCONNECT] 日志可统计）。

    • 上下文命中率：多轮对话中，LLM 有效用到历史的比例（可通过是否成功从 LocalRIS / ChatHistory 取到上下文来统计）。

  • 使用与粘性指标（技术可支持）

    • 活跃设备与使用频次：每日/每周活跃设备数、平均每日对话轮数（可由 c_stats + ChatHistory 推出）。

    • 语音时长与字数：累计 ASR 字数（AsrWordCount）、平均单次对话时长、单轮对话平均说话时长

项目为何采用 WebSocket 协议而非 HTTP2.0？

  • HTTP/2 更像是“高效的多路复用请求通道”，适合很多短请求；

  • WebSocket 更像是“一根永远不断的双向水管”，特别适合本项目这种“语音流 + 控制流 + 状态流混在一起、设备要长期在线”的 IoT 对话场景。

因此，从 实时性、双向性、实现复杂度、设备生态 几个角度综合考虑，选 WebSocket 是更合适、也更工程实用的方案。

并发连接数设定为 1000-2000 的依据是什么？

单实例并发连接数 1000–2000 的设定，是基于对机器硬件资源（CPU、内存、FD 限制）、WebSocket 连接开销、语音/LLM 业务并发模式的估算，并通过逐级压测（500/1000/1500/2000）验证，在资源占用 <70% 且错误率、断连率稳定的前提下选出的安全值；在线环境则通过网关限流 + 多实例分流保证单实例连接数维持在这一量级，并结合心跳与超时清理机制，确保 10
