网络基础

HTTP

一、什么是HTTP

概念

HTTP 是超文本传输协议，也就是HyperText Transfer Protocol。

协议：多个计算机之间通信、控制的规约。
传输：从A到B
超文本：文本、图片、视频、音频的复杂组合

状态码

2XX成功
301:永久重定向 302:临时重定向
400:用户请求有问题 403:用户权限不足 404:服务器没有该资源 405:请求方法出错
500:服务器报错 502:服务器作为网关访问后端服务器出错 503:服务器暂忙 504：超时

二、各版本HTTP特点

HTTP1.0

基础版本，没有长连接复用TCP，优点简单。可拓展、跨平台、应用广泛

HTTP1.1

在1.0的基础上增加长连接可复用TCP，且拥有以上优点，缺点就是无状态、明文传输不安全、队头阻塞

队头阻塞：虽然HTTP1.1有管道网络传输即请求发送后不用等待响应可以继续发，但没有应用，所以在HTTP1.1的情况下，发送一个请求后，必须等服务端响应后才嫩发送第二个请求，如果服务端存在阻塞，也会连带阻塞第二个请求。

HTTP2

相较于版本1引入了相同请求头可压缩，数据以二进制流传输虽然不利于人类阅读但利于计算机运算，服务器可主动推送资源，但其中最牛的还属在同一个TCP连接中引入多个Stream。每一个Stream可以作为一个请求发送，在服务端接收请求的时候可以按Stream处理并响应，可以做到按不同Stream顺序发送响应在宏观层面达到一种并发传输的效果。这虽然解决了HTTP层面的队头阻塞即请求智能一个一个发，但引来了TCP层的队头阻塞，因为TCP层是按顺序等待包到来的，如果1 2 3 4同时发送，1到了，3 4到了，但是2没有到，还是需要2重传到达之后才能读取3 4导致TCP队头阻塞，即使数据到了，也不能读取。

HTTP3

HTTP3将传输层协议从TCP改成了UDP，彻底解决队头阻塞问题，不再需要按顺序等待数据到达在读取，其中如果有数据丢失也是按相应的Stream进行重传，并不会影响其他流。更快的连接建立，其他两个版本的TCP与TLS是分别建立连接，而HTTP3只需要一个RTT就能建立连接判断双方的StreanID即可。高效的连接迁移，其他两个版本需要两个ip两个端口号的四元组才能标识一条连接，而QUIC只需要StreamID即可。

三、HTTP与HTTPS

区别

1、HTTPS在HTTP与TCP之间加入TLS/SSL层加密
2、HTTPS可以防范监听、篡改、伪造
3、HTTP端口号为80, HTTPS端口号为443

HTTPS的连接过程

首先进行TCP三次握手，然后进行TLS/SSL层的四次握手

1、客户端（生成随机数、确定TLS/SSL版本、加密算法）
2、服务端（生成随机数、确定TLS/SSL版本、加密算法、发送CA证书）
3、客户端（生成随机数，验证CA证书合法性、根据CA中的公钥加密三个随机数）
4、服务端（根据私钥解密客户端发送的加密后的三个随机数、后续都拿这个加密后的串作为密钥）

整个过程对称加密、非对称加密都用到了，因为非对称加密性能较差且如果私钥泄密后果不堪设想，对称加密性能高且需要仅双方知道。

四、与其他协议的关系

RPC

RPC（远程过程调用）并不是协议是一种思想，类似gRpc才是一种协议，并且RPC出的比HTTP还要早。在早期的CS架构中，一个客户端只需要连接自家公司的服务器即可只用rpc，到后来browse兴盛BS架构逐渐成为主流，且HTTP、RPC逐渐趋于同化，HTTP用户前端到后端通信，RPC用于后端内部服务间通信

WebSocket

WebSocket支持服务器主动推送资源，而不需要长轮询或者不断轮询。

TCP

一、概念

TCP是位于传输层的面向连接的、可靠的、基于字节流的传输协议，位于同层的UDP是无连接、不可靠、基于数据包交付的传输方式。

而TCP为了实现这些特点具有以下几个特有的功能，比如连接管理（三次握手、四次挥手）、重传、差错检验、流量控制、拥塞控制等。

与UDP的不同

1、TCP只支持一对一，UDP支持一对一、一对多、多对多
2、TCP有连接管理保障双方连接正常，UDP没有
3、TCP基于字节流传输有丢包、半包现象，UDP基于数据报传输，一个报文即一段数据
4、TCP有流量控制、拥塞控制根据网络及接收方接收能力控制发送快慢， UDP没有
5、TCP头部最低20个字节，UDP只用8个

TCP和UDP可以监听同一个端口，因为底层使用的接收程序不同，会根据包的不同使用不同的接收处理程序。

二、连接管理

三次握手

过程

1、客户端发送一个带有syn的包且序列号是x 客户端状态：syn_sent 服务端状态：listen
2、服务端接收该包并响应一个syn+ack的序列号为y且确认应答号为x+1的包 客户端状态：syn_sent 服务端状态：synrecv
3、客户端接收并响应一个带有ack的序列号为x+1确认应答号为y+1的包，至此连接建立成功。 客户端：established 服务端接收后进入established

在服务端第一次发包的时候会将该次连接加入半连接队列，使用一个哈希表（在加入全连接的时候以o1的时间复杂度获得该连接），在客户端发送的最后一次ack到达时，将连接加入全连接队列（使用列表，当调用accept的时候，将链表给内核程序进行处理）。

为什么是三次

三次是最少的确定双方都有发送和接收能力的连接次数且三次握手可以组织历史连接重复初始化导致的资源浪费。

连接报文丢失问题

第一次丢失：客户端因没有接收到服务端返回的ack报文会超时重传，重传到一定数量会关闭连接
第二次丢失：客户端会重传第一次的syn报文原因跟上面一致。服务端也会重传第二次，因为第二次会携带一个syn报文需要客户端进行ack，没有客户端的ack，所以服务端也会重传。
第三次丢失：服务端会重传，因没有收到客户端返回的ack，顾认为第二次丢失，而客户端的ack没办法确定是否重传。

SYN攻击

上文提到过半连接队列。在服务端第一次接收到客户端发送的syn报文时，会将该连接放入半连接队列，而四元组（发送ip，发送端口，接收ip，接收端口）确认一条连接。当有人利用重复变换的发送ip进行syn洪范攻击时，半连接队列会因为客户端持续的发送syn报文而不应答服务端发送的syn报文被撑爆，后续的正常连接会被拒绝。如何解决？增大半连接队列，减少syn+ack重传次数去释放掉一些连接，跳过半连接直接进入到全连接队列。

四次挥手

过程

1、主动方发送fin报文，关闭发送功能接收仍然正常 主动方状态：fin_wait1 被动方状态：established
2、被动方发送ack对其进行确认 主动方状态：fin_wait1 被动方状态：close_wait
3、被动方数据全部发送完毕，发送fin报文 主动方状态fin_wait2 被动方状态：last_ack
4、主动方接收后发送ack报文 主动方状态：time_wait 被动方状态：last_ack

为什么需要四次

因为服务端在收到客户端发送的fin报文时不能立刻关闭，可能还有数据待发送，如果没有数据发送，是可以压缩成三次的。

关闭报文丢失问题

第一次丢失：客户端因为没有收到服务端返回的ack报文导致超时重传，到一定数量后直接关闭连接
第二次丢失：同上
第三次丢失：服务端因为没有收到客户端返回的第四次挥手导致超时重传，到一定数量后关闭
第四次丢失：第四次主动发送端会进入2msl的time_wait阶段在该阶段如果没有收到被动方发送的第三次握手，会关闭连接，如果收到了，会重置time_wait阶段并发送第四次握手

为什么会有time_wait阶段

1、保证双方都优雅关闭
2、防止历史中的数据对后面相同四元组进行干扰，这个时间足以让双方的数据都自然消失，之后的数据必定是新连接建立的数据

time_wait过多有什么问题

1、占用端口资源
2、占用系统资源

服务端出现大量time_wait

出现该状态证明服务端是主动关闭方，可以概括为以下三个原因：
1、双方未使用长连接
2、长连接不再发送数据导致超时关闭
3、长连接上的请求数量达到上限

服务端出现大量close_wait

出现该状态证明服务端是被动关闭方且服务端没有调用close函数进行关闭，该状态一般是网络编程编码问题，导致没有处理关闭请求，而这些连接一直在close_wait状态下进行堆积。

已经建立连接的情况下出现故障

客户端故障：
有数据传输：一直超时重传，导致连接关闭
无数据传输：可以开启保活机制，达到一定时间发送类似ping的消息检测客户端是否存在，不存早连接关闭
服务端故障：
会自动发送fin报文进行主动关闭
